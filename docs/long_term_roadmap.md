# Skoll 长期主线计划

> 最后更新：2026-06-09
> 定位：Skoll 的长期目标是成为一个开源 Admin 框架，同时具备可治理的插件平台能力。路线参考 go-admin 的工程分层、hisiphp 的插件模块化经验，以及 Gin-Vue-Admin 的后台基础功能完整度。

## 1. 长期目标

Skoll 不只做一个后台控制台，而要沉淀成可复用的开源基础框架：

- 简化业务层开发：通过领域分层、CRUD 生成、Schema 表单/列表、通用导入导出降低重复劳动。
- 支持插件热插拔：插件可声明菜单、路由、权限、配置、资产、任务、发布策略，并进入统一治理。
- 形成成熟后台能力：用户、角色、权限、菜单、字典、部门、岗位、数据权限、文件、任务、审计、监控。
- 面向真实生产：质量门禁、性能基线、可观测、备份恢复、发布回滚和安全审计齐备。
- 面向开源生态：文档、示例插件、贡献规范、版本策略和插件开发教程完整。

## 10. 当前短期执行顺序

| 顺序 | 任务 | 原因 |
| --- | --- | --- |
| 1 | 建立质量基线 | 当前改动多，必须先知道真实失败项 |
| 2 | 修复 docs 编码并更新状态表 | 开源项目第一入口必须可信 |
| 3 | 系统设置 schema 后端化 | 打通配置、插件 schema、业务表单生成之间的桥 |
| 4 | 字典/部门/岗位 | Admin 框架绕不开的基础件 |
| 5 | 数据权限 | 依赖组织模型，服务真实后台项目 |
| 6 | CRUD 代码生成器 | 直接体现“简化业务层开发” |
| 7 | 插件风险/权限/市场 | 让插件能力从“能用”变成“可治理” |

## 11. 阶段性完成定义

S1 完成时，Skoll 应能支撑一个普通后台项目的基础管理需求；S2 完成时，应能明显减少业务模块重复开发；S3 完成时，插件热插拔应具备可治理、可发布、可回滚能力；S6 完成时，Skoll 应具备面向开源社区发布和持续协作的基本条件。
