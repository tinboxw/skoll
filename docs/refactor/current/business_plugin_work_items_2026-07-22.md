## Pharma OA Extraction Boundary

The host implementation is not a compatibility source and is not moved mechanically into the plugin. Business behavior that remains in scope is rebuilt against the current public plugin SDK; obsolete host code is deleted.

| Host capability | Disposition | Plugin owner |
| --- | --- | --- |
| Employee, customer, supplier, product, catalog, qualification, general OA, purchase, inbound | Keep only the independent implementation already delivered | BF4-02..BF5-03 |
| Customer contacts, visits, opportunities, follow-ups | Delete the host implementation; rebuild through public contracts | BF5-02 |
| Sales orders, allocation, picking, delivery | Delete the host implementation; rebuild through public contracts | BF5-04 |
| Warehouses, lots, balances, movements, transfers, counts, adjustments, returns | Delete the host implementation; rebuild through public contracts | BF5-05 |
| Quality complaint, inspection, quarantine, release, cold chain, recall, adverse events | Delete the host implementation; rebuild through public contracts | BF5-06 |
| Contracts, invoices, payment plans, reminders, reconciliation | Delete the host implementation; rebuild through public contracts | BF5-07 |
| Medical operations pages and navigation | Delete host pages; keep all business UI inside the installed plugin | BF5-08 |
| Compliance dashboards, alerts, reports, exports, demo seed | Delete host features and fixtures; rebuild only verified product requirements | BF5-09 |
| Workflow, datastore, document numbers, files, jobs, notifications, audit, permissions, data scope, secrets, configuration, frontend host bridge | Retain as industry-neutral framework services | BF1..BF3 |

Purity checks target production ownership. Generic plugin-platform tests may use `pharma_oa` as an opaque plugin identifier, and packaged lifecycle tests may reference the independent package; neither may import or reconstruct a host business implementation.
