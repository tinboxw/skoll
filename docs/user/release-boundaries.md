# 发布、监管与支持边界

[English](release-boundaries.en.md) | 简体中文

> 状态：当前公开发布与运营边界的中文默认说明。本文不构成法律、监管或专业意见。

## 发布定位

Skoll 是处于持续建设阶段的开源管理框架。`pharma_oa` 是用于展示插件平台、权限、审计、工作流、主数据和进销存能力的行业样板。仓库中的验收结果证明对应软件契约在记录环境中通过，不等同于对任何生产部署、组织流程或法规符合性的认证。

## 医药与监管边界

- `pharma_oa` 不是经监管验证的 GSP、GMP、医疗器械、临床或药品追溯系统，也不提供监管认证。
- “合规”“资质”“召回”“冷链”“审计”等功能名称只描述样板业务能力，不表示满足特定国家、地区、企业或监管机构要求。
- 本项目不提供医疗建议、临床决策、药品质量判定、法定记录签署或监管申报能力承诺。
- 采用者必须自行识别适用法律、行业规范、数据驻留、电子记录、验证、留存和审计要求，并由其法律、质量、信息安全和业务负责人完成上线批准。
- 未完成需求确认、风险评估、计算机化系统验证、权限复核、备份恢复演练和操作规程前，不应将样板直接用于受监管生产流程。

## 演示与数据安全

仓库内置的 `DEMO-*` 编号、姓名、联系方式、机构、药品、证照和交易记录均为虚构测试数据，不代表真实人员、患者、客户、供应商、药品批准文号或监管记录。不要把演示 seed 应用于生产数据库，也不要把真实个人信息、健康信息、商业秘密或生产凭据提交到仓库、Issue、日志、截图或验收证据。

| 责任项 | 运营要求 |
| --- | --- |
| 数据持久化 | `mysql` / `postgres` 模式持久化业务数据；`memory` 模式仅用于开发验收，进程结束即丢失 |
| 数据最小化 | 只采集业务必需字段，建立合法性、授权、访问和删除流程 |
| 权限与审计 | 按最小权限分配角色，定期复核数据范围和关键审计事件 |
| 加密与密钥 | 传输链路使用 TLS，数据库、备份和对象存储按组织策略加密；密钥进入专用密钥管理系统 |
| 留存与删除 | 由采用者定义数据库、日志、审计、导出和对象文件的留存及删除策略 |
| 备份与恢复 | 数据库、`/app/data`、`/app/plugins` 和外部对象存储分别纳入备份；发布前验证隔离恢复 |

部署、升级和恢复命令见 [部署、升级与恢复](deployment.md)，日常检查见 [运维手册](operations.md)。

## 安全与密钥

- 生产环境必须更换默认管理员密码和 `SKOLL_SECURITY_JWT_SECRET`，数据库、插件及外部服务凭据不得写入代码、镜像、Compose/Kubernetes 明文清单或发布证据。
- 发布前应固定依赖与镜像版本，审查插件来源、签名、权限、菜单、路由和迁移风险，并验证禁用和失败状态。
- 漏洞不得携带利用细节公开提交。按仓库 [安全策略](../../SECURITY.md) 请求私密报告渠道。
- 项目维护者不持有部署方的生产密钥，也不能替代部署方执行事故响应、取证或数据恢复。

## 许可证边界

- Skoll 源代码按仓库根目录 [MIT License](../../LICENSE) 提供，分发副本或重要部分时必须保留版权和许可声明。
- MIT License 按“原样”提供软件，不包含适销性、特定用途适用性和不侵权保证；准确条款以 `LICENSE` 为准。
- Go、Node.js、容器基础镜像、前端库及其他第三方组件保留各自许可证。`go.mod`、`go.sum`、`web/package.json` 和锁文件是依赖清单，不代表第三方许可证已经由本项目重新授权。
- 发布者必须为实际构建生成并审查 SBOM/第三方许可证清单，满足归属、通知、源码提供或其他适用义务。
- 除文件另有说明外，仓库中的示例插件、脚本和虚构演示数据随项目代码按 MIT License 分发；这不授予第三方商标、真实药品、真实机构或监管认证的权利。

## 支持边界

社区 Issue、讨论和贡献审核按维护者可用时间尽力处理，不提供商业支持、响应时限、可用性、数据恢复、监管验证或安全值守 SLA。问题报告应包含版本、环境、最小复现和已脱敏日志；一般问题不得包含漏洞细节或真实敏感数据。安全问题遵循 `SECURITY.md`，行为规范遵循 [CODE_OF_CONDUCT.md](../../CODE_OF_CONDUCT.md)。

生产部署方负责容量规划、监控告警、值班、升级窗口、回滚决策、灾难恢复和供应商支持安排。需要合同化服务时，应由采用者另行选择具备相应资质和责任能力的服务方。

## 发布前确认

1. 阅读并执行 [发布清单](../release-checklist.md) 与 [部署演练报告](../refactor/current/deployment_recovery_rehearsal_2026-07-21.md)。
2. 确认目标部署未启用默认凭据或演示 seed，真实数据已完成分类分级和授权评审。
3. 记录许可证/SBOM、镜像 digest、配置、密钥引用、备份、恢复点、回滚负责人和已接受风险。
4. 确认产品文案和合同没有把样板描述为已获认证、合规保证或医疗决策系统。
5. 不增加旧 API、旧数据结构、旧插件格式或旧页面路径兼容层；升级按当前契约和恢复点执行。
