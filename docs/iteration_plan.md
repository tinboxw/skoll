## 1. 计划概述

### 1.1 前期评估总结

根据前期功能实现状态评估，Skoll项目**后端核心功能已完整实现**（M0-M11阶段），包括：
- ✅ 基础设施与配置管理
- ✅ 领域模型与仓储设计
- ✅ 多数据库存储层实现（MySQL/PostgreSQL/ClickHouse）
- ✅ 多级缓存层实现（Redis/Memcached/Local）
- ✅ 业务服务层与API接口层
- ✅ 事件总线与异步处理
- ✅ 插件化架构完整实现

| **P2** | 代码质量优化 | ⚠️ 部分完成 | 技术债务清理 |

### 1.3 计划目标

| 目标类别 | 具体目标 | 量化指标 |
|---------|---------|---------|
| **功能完整性** | 前端管理界面完整 | 5个核心模块全部实现 |
| **质量保障** | 测试覆盖率达标 | ≥ 80% |
| **性能指标** | 系统性能优化 | QPS ≥ 500, 响应时间 < 150ms |
| **文档完善** | 文档体系完整 | API文档+用户文档+开发文档 |

### 1.4 项目注意事项（强制）

> 生效时间：立即生效（项目初始阶段）

1. 当前项目所有系统改造不考虑任何老旧系统、老旧数据结构或兼容层。
2. 首要目标是建立完善、规范、可长期演进的技术基建，不以短期兼容为代价。
3. 数据库层面严格要求：
    - 立即停止新增任何"兼容老旧数据"的临时表与映射表。
    - 彻底删除所有老旧数据及相关老旧表结构。
    - 前后端代码、数据库设计、前端实现全部切换为全新数据结构。
    - 严格执行新的数据规范，不保留回退路径和兼容分支。
4. 用户数据模型强制规范：
    - 用户表采用"账号 + 名称"字段模式。
    - 禁止使用 `displayname` / `display_name` 字段。

## 3. 里程碑详细规划

### M12: 前端项目基础框架搭建

#### 1. 功能项名称及简要描述

**前端项目基础框架搭建**：创建Vue 3 + Element Plus项目骨架，实现基础布局组件和登录认证功能。

#### 2. 详细功能需求

| 功能点 | 描述 | 用户场景 |
|-------|------|---------|
| 项目初始化 | 使用Vite创建Vue 3项目，集成Element Plus | 开发人员启动前端开发 |
| 登录页面 | 用户名密码登录、JWT token存储 | 管理员登录后台系统 |
| 布局组件 | 侧边栏导航、顶部栏、主内容区 | 系统统一布局 |
| 权限拦截 | 路由守卫、按钮级权限控制 | 未登录用户跳转登录页 |
| 状态管理 | Pinia状态管理配置 | 用户信息、菜单状态管理 |

| 状态管理 | Pinia | 2.1+ | 状态管理 |
| 路由 | Vue Router | 4.3+ | 路由管理 |
| 构建工具 | Vite | 5.2+ | 构建工具 |
| 样式 | SCSS | - | CSS预处理器 |
| 图标 | Lucide Vue | -next | 图标库 |

| 验收项 | 成功指标 |
|-------|---------|
| 项目结构 | 目录结构清晰，符合规范 |

### 8.1 安全机制缺陷

### 12.2 结构不合理问题点

#### 12.2.1 模块划分不一致

| 问题描述 | 影响分析 |
|---------|---------|
| `service/` 层按业务域划分子目录（`audit/`, `rbac/`, `role/`） | 便于维护 |
| `repository/` 层所有接口放在同一目录，未按业务域划分 | 文件过多，难以维护 |
| `handler/http/v1/` 层所有handler放在同一目录 | 查找特定业务代码困难 |

#### 12.2.2 Store层结构混乱

| 问题描述 | 影响分析 |
|---------|---------|
| `store/sql/gormrepo/store/` 嵌套过深 | 路径过长，难以理解 |
| `model/` 与 `store/` 分离 | 增加理解成本 |
| `mysql/` 和 `postgres/` 只有adapter，没有store实现 | 结构不一致 |

#### 12.2.3 Handler层版本管理缺失

| 问题描述 | 影响分析 |
|---------|---------|
| 只有一个版本v1，缺少版本管理规划 | 无法支持API演进 |
| 没有统一的路由注册入口 | 路由分散难以管理 |
| `response.go` 和 `response_helpers.go` 职责不清 | 职责边界模糊 |

#### 12.2.4 依赖关系复杂

| 问题描述 | 影响分析 |
|---------|---------|
| `bootstrap/` 依赖过多模块，成为"上帝包" | 耦合度高，难以测试 |
| 插件系统与核心模块耦合度高 | 扩展性受限 |
| 缺少依赖注入容器的清晰边界 | 职责不清 |

## 15. API接口前缀策略（方案B）

### 15.1 策略概述

根据需求分析，**采用方案B：`/skoll/` 统一前缀策略**，为所有API接口添加统一的路径前缀。

**推荐的完整API路径结构：**

```
# 核心API
GET    /skoll/v1/users              # 用户列表
POST   /skoll/v1/users              # 创建用户
GET    /skoll/v1/users/{id}         # 用户详情
PUT    /skoll/v1/users/{id}         # 更新用户
DELETE /skoll/v1/users/{id}         # 删除用户

GET    /skoll/v1/roles              # 角色列表
POST   /skoll/v1/roles/{id}/grant   # 角色授权

POST   /skoll/v1/rbac/check         # 权限检查

GET    /skoll/v1/audit              # 审计日志列表
GET    /skoll/v1/audit/export       # 审计日志导出

GET    /skoll/v1/system/settings    # 系统配置

# 插件API
GET    /skoll/v1/plugins            # 插件列表
POST   /skoll/v1/plugins/{id}/enable # 启用插件

# 插件扩展路由
GET    /skoll/plugin/{pluginId}/xxx # 插件自定义路由

# 健康检查
GET    /skoll/health                # 健康检查

# 文档
GET    /skoll/docs/openapi.yaml     # OpenAPI文档
GET    /skoll/docs/swagger          # Swagger UI
```

### 15.2 策略优势分析

| 维度 | 说明 |
|------|------|
| **品牌一致性** | 与Go Module命名（`github.com/tinboxw/skoll`）保持一致 |
| **冲突规避** | 独特名称降低路径冲突风险，便于多系统共存部署 |
| **安全性** | 便于配置Nginx路径隔离、WAF规则、访问控制 |
| **可维护性** | 路由分组清晰，便于Swagger文档分组展示 |
| **扩展性** | 为插件路由、多租户支持预留清晰边界 |
